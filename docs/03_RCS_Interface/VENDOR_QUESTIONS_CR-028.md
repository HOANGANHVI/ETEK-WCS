# Questions for the RCS vendor – CR-028 (RCS-managed dispatch)

Reference: RCS-2000 API Developer Guide **V3.3** (UD35865B, 2023-12-04). WCS has implemented RCS-managed dispatch **on the simulator only**; the answers below decide the real adapter. Nothing was assumed in place of an answer.

| # | Question | Why it matters / what the document says |
|---|---|---|
| 1 | **Repeating a request with the same `reqCode`:** what does `genAgvSchedulingTask` return when the first call was received but the answer was lost? The same success answer, or code `6` ("no need to resend, the task of the same reqCode is not completed")? Is a new task ever created for a repeated `reqCode`? | WCS keeps `reqCode` unchanged on retry (section 5.2.1: "the request ID must be same") and checks the task status before re-sending. The behaviour on a repeat is not described. |
| 2 | **Meaning of `data` in the `genAgvSchedulingTask` response** ("custom content, such as task ID", the sample shows `F01169C808C317111G`): is it the `taskCode` WCS supplied (when WCS sets `taskCode`), or an RCS-generated id? Is it the value to use in `queryTaskStatus.taskCodes[]` and in the callback `taskCode`? | WCS must correlate the task with `queryTaskStatus` and `agvCallback`. |
| 3 | **Authentication of `agvCallback`:** the document describes `tokenCode` only for calls WCS makes to RCS. How does RCS authenticate itself when it calls the WCS callback URL (`/xxx/agv/agvCallbackService/agvCallback`)? Is the path configurable, and which source addresses call it? | The real callback endpoint is not implemented until this is known. |
| 4 | **Can one AMR have more than one active task** (queued tasks of the same robot) at the same time? | Decides whether WCS may assume one active task per `agvCode`. WCS does not assume it in RcsManaged mode. |
| 5 | **Does the RCS change the robot during a task** (for example `taskStatus` "6" resending, or after an exception)? If it does, does `queryTaskStatus.agvCode` change and is a callback sent? | WCS records a robot change as a history event and follows the latest `agvCode`. |
| 6 | **`continueTask` when the RCS selects the robot:** which parameters identify the task (`wbCode` + `podCode`), and does it work without `agvCode`? How does a multi-sub-task task (WaitingForDestination → Continuing in WCS) map to RCS sub tasks? | Needed for flows with a continue step. Not simulated beyond the existing behaviour. |
| 7 | **Task lifecycle / status:** (a) when exactly does `agvCode` appear in `queryTaskStatus` (before `start`, at `start`)? (b) mapping of `taskStatus` 0, 3, 6, 10 to WCS states (sending exception, sending, resending, interrupted) and which are final; (c) is `cancelTask` accepted for a task that has no robot yet; (d) is the `queryTaskStatus` frequency limited (the document limits only `queryAgvStatus`)? | WCS tracks the integration state NotSent / Sending / Accepted / AwaitingAssignment / Assigned / SyncError and must know which `taskStatus` values are final. |
| 8 | **Location and task-type mapping (blocks the real create-task adapter):** the RCS position code (`positionCodePath.positionCode` and `type` "00"-"13") of each WCS location A1…F5, the `taskTyp` ("F01"…) and `podTyp`/`podDir`/`priority` rules for BP01-BP06. | Not in any project document; the real `genAgvSchedulingTask` adapter is not implemented without it. |
| 9 | **`continueTask` – same AMR?** Section 5.2.2 says "continue executing the next sub task"; the task is found by `wbCode`/`podCode`/`agvCode`/`taskCode` (all optional). Does the continued task always run on the **same AMR** that executed the previous sub task? Is that guaranteed, or can the RCS re-plan to another AMR? | Section 4.2 describes "the AMR keeps carrying the rack and waits until the third-party platform calls an API to continue the task, then carries the rack back". The text does not say whether the AMR may change. WCS (RcsManaged) will not follow a change of AMR while the rack is on the AMR (it records `LEG_ROBOT_CHANGE_REFUSED`). |
| 10 | **Does the AMR keep the rack after the pick (AfterPick flows)?** Between the pick and `continueTask`, does the AMR stay at / near the pick point holding the rack, and for how long may it wait? Is there a time-out after which the RCS releases the AMR or the task? | BP-01, BP-03 and BP-06 choose the destination after the pick (`nextPosition` "required when the task type is externally configured"). WCS keeps the rack IN_TRANSIT and waits (WAITING_FOR_DESTINATION) without a limit. |
| 11 | **Can the RCS change the AMR between two sub tasks or two tasks that carry the same rack?** If yes, under which conditions (fault, charging, re-plan), and is a callback / status change sent? | Needed to decide whether WCS must treat a change as a hand-over. |
| 12 | **Hand-over between two AMRs:** is there any RCS API / procedure to hand a rack from one AMR to another (or to have the second leg executed by the **same** AMR, for example by sending `agvCode` of the previous leg in `genAgvSchedulingTask`)? What does the RCS do when the requested `agvCode` is busy: queue, reject, or choose another? | Today every leg is an independent task and the RCS chooses. If the owner requires continuity between legs, the only documented lever is the optional `agvCode`; its behaviour is not described. WCS does **not** implement any hand-over or pinning. |
| 13 | **`agvCode` in `queryTaskStatus` for a leg that waits for `continueTask`:** is `agvCode` present while the task waits for the continue call? Does it stay the same until the task ends? | WCS records the AMR of each leg from this field (`transport_legs.RobotCode`) and re-checks every `Rcs:Dispatch:AssignedRecheckSeconds`. |
| 14 | **Completion of a leg waiting for `continueTask`:** which `taskStatus` / callback `method` does the RCS report when the AMR has put the rack down (drop) versus when the whole task ends? Is there an event that confirms the rack was placed at the position (not only that the AMR left)? | WCS never treats "task completed" as a hand-over; it needs its own drop confirmation. Knowing what the RCS reports helps to cross-check, but WCS does not rely on it. |
| 15 | **Keeping the AMR across sub tasks (if a process must use the same AMR):** which RCS mechanism guarantees it (a single task with several sub tasks and `continueTask`, a held AMR, `agvCode` on the next request)? | WCS will not send the previous leg's `agvCode`, and will not implement a "same AMR" process until the RCS confirms its mechanism. |
| 16 | **CR-030 – `taskCode` and `reqCode`:** WCS sends its own request code (36 characters) as `taskCode` (max 64, "Task ID – if not configured the system generates automatically") and a deterministic hash of it (32 characters) as `reqCode` (max 32). Is `taskCode` honoured exactly and returned in `queryTaskStatus` and in the `agvCallback`? Is the response `data` of `genAgvSchedulingTask` the same task id? | WCS identifies the RCS task only by this code; `data` is never used. |
| 17 | **CR-030 – what must the first request carry for each template (BP-01…BP-06)?** `taskTyp`, `positionCodePath` (which positions: the pick position only, or pick and drop), `podDir`, `podTyp`, `priority`, `taskMode`; and, for a destination chosen after the pick, does `continueTask` with `nextPositionCode` apply to the configured `taskTyp`? | The mapping is configuration (`Rcs:RealDispatch:Processes`, `Locations`); empty until the RCS engineer confirms it. |
| 18 | **CR-030 – callback authentication and delivery:** can the RCS send a custom header (WCS expects `X-Rcs-Callback-Token`) or is a reverse proxy needed? From which source address(es) does it call? What does the RCS do when the answer is not `"code":"0"` (retry interval, count)? Is the base path configurable (`/xxx/agv/agvCallbackService/agvCallback`)? | WCS refuses callbacks unless a secret and/or allowed sources are configured; it invents no scheme. |
| 19 | **CR-030 – `cancelTask`:** which `forceCancel` mode applies to a task whose AMR carries a rack ("0": rack put down at the current location)? What does the RCS report about where the rack was put? Is a cancel accepted for a task that has no AMR yet? | The rack position becomes uncertain; WCS then reconciles (it never assumes a position). |
| 20 | **CR-030 – `queryTaskStatus`:** call-frequency limit? What does it answer for an unknown `taskCode` (empty `data`, or an error code)? Is `agvCode` present while the task waits for `continueTask`? | WCS polls every `AssignmentCheckSeconds` and treats an empty `data` as "the RCS does not know the task". |
| 21 | **CR-030 – meaning of `end` and `outbin`:** does `end` mean the AMR released the rack at the destination (not only that the AMR finished moving)? When is `outbin` sent? | WCS never completes a task or confirms a drop from `end`; it needs its own confirmed drop (CR-028 section 13, D-4). |
